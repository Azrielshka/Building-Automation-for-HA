# JavaScript Guidelines — Custom Panel (vanilla JS + Lit, без сборки)

Язык-специфичные правила для панели пусконаладчика (ТЗ §5.2). Дополняет ядро
[`styleguide.md`](styleguide.md).

**Решение по стеку:** vanilla JS + Lit, **без шага сборки**. Исходники — обычные
`.js`-модули, которые HA отдаёт как есть. Lit подключается вендоренной копией из
репозитория (§2) — не из npm, не с CDN и не заимствованием у фронтенда HA.

Следствие: типы даёт не компилятор, а JSDoc + `tsc --checkJs --strict` — проверка
без компиляции. Файлы остаются `.js`, `tsc` ничего не генерирует.

Версии и команды — в [`tooling.md`](tooling.md).

---

## 1. Почему без сборки

Панель деплоится на Home Assistant OS. Каждый шаг сборки — это то, что может
разойтись между машиной разработчика и целевым устройством, и что придётся
воспроизводить при каждой правке в поле. Пусконаладчик правит конфиг на объекте;
цена «пересобрать бандл» там несоизмерима с выгодой.

Отсюда жёсткие следствия, которые нельзя обойти «только в этот раз»:

- **Никаких импортов из `node_modules` в рантайм-коде.** `node_modules`
  существует только для dev-инструментов (`tsc`, `eslint`, `prettier`).
  Единственная рантайм-зависимость — вендоренный Lit (§2), и он подключается по
  относительному пути, а не по имени пакета.
- **Никакого TypeScript-синтаксиса** в `.js`: ни аннотаций типов, ни `enum`, ни
  декораторов Lit (`@property`, `@customElement`) — они требуют транспиляции.
  Вместо декораторов — статические поля (`static properties = {...}`).
- Только то, что понимает браузер напрямую: ES-модули, `class`, `async/await`,
  опциональная цепочка.

## 2. Lit — вендоренный, не заимствованный

**Lit лежит в репозитории.** Это осознанное решение, а не временный костыль.

Почему не взять у HA: фронтенд HA действительно собран с Lit 3.3.3, но в шаблоне
страницы **нет import map**, поэтому bare-спецификатор `import { LitElement }
from "lit"` из стороннего модуля не разрешится. Официального поддерживаемого
способа дотянуться до внутреннего Lit не существует. Ходовой в сообществе трюк
`Object.getPrototypeOf(customElements.get("ha-panel-lovelace"))` — **запрещён**:
он держится на непубличной детали реализации фронтенда и молча ломается при
любом его рефакторинге, причём уже на объекте.

Почему не CDN: официальная дока по кастомным панелям показывает импорт с unpkg,
но она устарела (там LitElement 2.4.0, на два мажора старше). Объект может быть
без интернета — панель, которая не грузится без внешней сети, неприемлема.

```
custom_components/building_automation/www/
├── vendor/
│   └── lit-3.3.3.js        # прибитая версия, не редактируется руками
├── panel.js
└── components/
```

```js
// ХОРОШО — относительный путь до вендоренной копии, версия видна в имени файла
import { LitElement, html, css } from "./vendor/lit-3.3.3.js";

// ПЛОХО — не разрешится: import map в HA отсутствует
import { LitElement } from "lit";

// ПЛОХО — зависимость от внешней сети
import { LitElement } from "https://unpkg.com/lit@3.3.3/index.js?module";

// ПЛОХО — реверс непубличных внутренностей фронтенда HA
const LitElement = Object.getPrototypeOf(customElements.get("ha-panel-lovelace"));
```

Правила обращения с вендоренным файлом:

- Версия — **в имени файла**. Обновление Lit = новый файл + правка импортов, а не
  молчаливая подмена содержимого.
- Файл не патчится руками. Никогда.
- Обновляется отдельным коммитом, который больше ничего не меняет.
- Версия фиксируется в [`tooling.md`](tooling.md) §7.

## 3. Контракт панели с Home Assistant

Панель — это custom element, который HA создаёт и кормит четырьмя свойствами:
`hass`, `narrow`, `route`, `panel`. Три правила про них.

### `hass` пересоздаётся — не кэшируйте его куски

Объект `hass` заменяется целиком при **каждом** изменении состояния в системе.
Сохранённая ссылка на `hass.states` мгновенно протухает.

```js
// ПЛОХО — снимок устареет на первом же изменении состояния
constructor() {
  super();
  this._states = this.hass.states;
}

// ХОРОШО — читаем из актуального hass в момент использования
get _scheduleState() {
  return this.hass?.states[this._scheduleEntityId];
}
```

### Никогда не мутируйте `hass`

`hass` принадлежит фронтенду HA. Запись в него (`this.hass.states[x] = ...`,
`this.hass.foo = ...`) ломает чужие компоненты непредсказуемым образом.
Состояние меняется только через сервисные вызовы и WebSocket-команды.

### Не перерисовывайте панель на каждый `hass`

`hass` прилетает десятки раз в секунду на живом объекте. Рендер по каждому — это
подвисающий UI. Сравнивайте то, что вам реально нужно.

```js
// ПЛОХО — рендер на любое изменение любой сущности в доме
set hass(value) {
  this._hass = value;
  this.render();
}

// ХОРОШО — реагируем только на интересующие нас сущности
shouldUpdate(changed) {
  if (!changed.has("hass")) return true;
  const old = changed.get("hass");
  return WATCHED.some((id) => old?.states[id] !== this.hass.states[id]);
}
```

## 4. Подписки и утечки

Панель монтируется и размонтируется при каждом переходе по интерфейсу HA.
Не снятая подписка живёт вечно и дублируется при следующем открытии панели.

**Всегда флагать** `subscribeEvents`, `subscribeMessage`, `addEventListener`,
`setInterval`, `setTimeout` без парного снятия в `disconnectedCallback`.

```js
// ПЛОХО — открыл панель трижды, обработчик вызывается трижды
async connectedCallback() {
  super.connectedCallback();
  this.hass.connection.subscribeEvents(this._onModeChanged, "building_mode_changed");
}

// ХОРОШО — храним unsub и снимаем при отключении
async connectedCallback() {
  super.connectedCallback();
  this._unsub = await this.hass.connection.subscribeEvents(
    this._onModeChanged,
    "building_mode_changed",
  );
}

disconnectedCallback() {
  super.disconnectedCallback();
  this._unsub?.();
  this._unsub = undefined;
}
```

Подписка асинхронная: если элемент отключили до того, как промис
разрезолвился, `_unsub` придёт уже после `disconnectedCallback`. Проверяйте
`this.isConnected` перед сохранением и снимайте сразу, если элемент уже мёртв.

## 5. Обмен с ядром интеграции

Панель говорит с Python-частью **только** через WebSocket-команды интеграции.

- Никаких REST-запросов к своим эндпоинтам — команд WS достаточно, и они уже
  аутентифицированы.
- Никакой записи конфигурации в обход ядра. Панель не знает про `.storage` —
  она отправляет команду, ядро валидирует и сохраняет (см. `python-guidelines.md` §3).
- Все команды именуются с префиксом домена: `building_automation/config/get`,
  `building_automation/config/save`, `building_automation/topology/update`.

```js
// ХОРОШО — типизированный вызов команды ядра
/**
 * @param {BuildingConfig} config
 * @returns {Promise<{ saved: boolean }>}
 */
async _saveConfig(config) {
  return this.hass.callWS({
    type: "building_automation/config/save",
    config,
  });
}
```

Ответ WS-команды — **недоверенный вход** ровно так же, как и в Python. Не
считайте, что пришло то, что вы ожидали: проверяйте перед использованием.

## 6. Типизация через JSDoc

Строгость закрывается `tsc --checkJs --strict`. Это даёт настоящую проверку типов
в обычных `.js`.

- Общие структуры (конфиг здания, профиль режима, узел топологии) описываются
  один раз в `types.js` через `@typedef` и импортируются в остальные модули.
- Формы данных должны **совпадать с дата-классами Python**. Расхождение схемы
  панели и схемы ядра — источник самых дорогих багов в проекте; при правке
  одной стороны правится и вторая, в одном коммите.
- `@ts-ignore` / `@ts-expect-error` — только с обоснованием в комментарии рядом.

```js
/**
 * @typedef {object} ModeProfile
 * @property {string} modeId          Идентификатор режима ("lesson", "break").
 * @property {number} delaySeconds    Системная задержка перед применением.
 * @property {ServiceAction[]} actions
 */
```

## 7. Анти-паттерны, флагаемые в ревью

- `console.log` в рабочем коде. Отладочный вывод — либо убран, либо через общий
  логгер с флагом. Логи панели сыплются в консоль браузера диспетчера.
- `innerHTML` со значениями, пришедшими из конфига или от пользователя —
  XSS. Только шаблоны Lit (`html\`...\``), они экранируют интерполяцию.
- `==` вместо `===` (исключение — `== null` для проверки null и undefined разом).
- Промис без `await` и без `.catch` — необработанный rejection, который в
  проде проявится молчаливой пропажей сохранения.
- Пустой `catch {}` — то же правило fail fast, что и в Python: ловим конкретное,
  иначе пробрасываем.
- Мутация аргументов функции.
- Тяжёлые вычисления в геттерах, вызываемых из `render()`.

## 8. Стиль

- `camelCase` — переменные и функции, `PascalCase` — классы, `UPPER_SNAKE` —
  константы модуля.
- Приватные поля компонента — с префиксом `_`.
- `const` по умолчанию, `let` только там, где переменная действительно
  переприсваивается. `var` запрещён.
- Форматирование — `prettier`, конфликты стиля не обсуждаются вручную.
- Имя custom element — с префиксом домена: `<building-automation-panel>`,
  `<building-automation-mode-matrix>`. Глобальный реестр элементов один на весь
  фронтенд HA; безпрефиксное имя рано или поздно столкнётся с чужим.

## 9. Definition of Done (фронтовая часть)

- [ ] `tsc --checkJs --strict` — 0 ошибок.
- [ ] `eslint` — 0 ошибок.
- [ ] `prettier --check` — без диффов.
- [ ] Нет `@ts-ignore` без обоснования, нет `console.log`.
- [ ] Каждая подписка/таймер снимается в `disconnectedCallback` — проверено
      открытием и закрытием панели несколько раз подряд без роста числа
      обработчиков.
- [ ] Панель не пишет ничего в обход WS-команд ядра.
- [ ] Шага сборки нет: файлы в `www/` отдаются браузеру ровно в том виде, в каком
      лежат в репозитории.
- [ ] Единственная рантайм-зависимость — `www/vendor/lit-<версия>.js`; импортов
      по имени пакета, с CDN и обращений к внутренностям фронтенда HA нет.
- [ ] Панель открывается на объекте **без доступа в интернет**.
