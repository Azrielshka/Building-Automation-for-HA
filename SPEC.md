## 1. Контекст

**Что делаем.** Кастомная интеграция Home Assistant, которая вычисляет режим
работы здания (Урок / Перемена / Не рабочее время / Окошко) из внешнего
расписания и каскадно применяет к помещениям профили этих режимов: сервисные
вызовы к групповым светильникам и разрешение либо запрет работы автоматизаций по
датчикам движения.

**Где границы.** Периметр — от объекта до **помещения** включительно. Зоны
внутри помещения и отдельные светильники ведёт система датчиков (`zone_manager`).
Топологию (Floors, Areas, групповые светильники) ведёт генератор
`ha-lighting-compilers`. Интеграция не создаёт `script.*` / `automation.*`, не
работает с протоколами оборудования и не следит за здоровьем устройств.

**Ключевые ограничения среды:**

- Целевой Home Assistant Core **2026.5.4**, Python **≥ 3.14.2**.
- Пакет `homeassistant` в проекте **не устанавливается**; тесты с ним не
  гоняются. Отсюда главное архитектурное требование — §2.1.
- Фронтенд панели — vanilla JS + Lit без сборки.

**Источники требований.** Архитектурные требования и журнал решений —
[`docs/requirements/TZ.md`](docs/requirements/TZ.md) (редакция 5). Постановка и пользовательские сценарии —
[`docs/requirements/task.md`](docs/requirements/task.md). Доменный словарь — [`CONTEXT.md`](CONTEXT.md).
Контракт со смежным проектом —
[`docs/contracts/contract-ha-lighting-compilers.md`](docs/contracts/contract-ha-lighting-compilers.md).
Правила кода — [`.ai/rules/`](.ai/rules/).

**Термины** используются строго по `CONTEXT.md`: объект, этаж, помещение, зона,
режим управления, режим расписания, профиль, каскад, схлопывание, гейт,
инвариант Area, отложенный переход.

## 2. Архитектура

### 2.1. Принцип: функциональное ядро — императивная оболочка

Пакет `homeassistant` не устанавливается, значит **всё, что зависит от `hass`,
непроверяемо автоматически**. Единственный способ иметь осмысленное покрытие —
вынести политику в чистые функции, оставив в обвязке только передачу данных.

Отсюда конструкция:

```
   Входные данные (снимки)              Решение (данные)
          │                                   │
          ▼                                   ▼
   ┌──────────────────────────────────────────────┐
   │  ЯДРО  domain/   — чистые функции, без hass  │
   │  вход: снимок состояния + событие + время    │
   │  выход: новое состояние + команды + события  │
   └──────────────────────────────────────────────┘
          ▲                                   │
          │ снимки собирают адаптеры          │ решение исполняют адаптеры
   ┌──────┴───────────────────────────────────▼───┐
   │  ОБОЛОЧКА  — адаптеры Home Assistant         │
   │  реестры, сервисы, шина, таймеры, Store, WS  │
   └──────────────────────────────────────────────┘
```

Ядро **ничего не выполняет**: оно возвращает описание того, что должно
произойти. Побочные эффекты живут только в оболочке.

Проверка **deletion test** для ядра: если убрать `machine.decide` и разложить
его логику по обработчикам событий Home Assistant, сложность не исчезнет — она
размажется по пяти-шести местам (обработчик расписания, обработчик таймера,
обработчик переключателя, старт, изменение реестра), и ни одно из них не будет
покрыто тестами. Сложность концентрируется — модуль зарабатывает своё
существование.

### 2.2. Модули ядра

Шесть модулей. Для каждого указан **интерфейс** (всё, что обязан знать
вызывающий) и в чём его **глубина**.

#### 2.2.1. `domain/schedule.py` — разрешение расписания

```python
def resolve_schedule_mode(
    events: Sequence[ScheduleEvent],
    fallback: ScheduleMode,
) -> ScheduleResolution: ...
```

**Интерфейс.** Вход — снимок сущностей источника (`event_type`, активна ли,
доступна ли). Выход — режим, признак доступности источника и, если было
наложение, его описание. Функция тотальна: не бросает исключений, на любом входе
возвращает результат. Порядок элементов на результат не влияет.

**Глубина.** За одним вызовом скрыты: приоритет `break > window > lesson > off`,
детект наложения, пустой вход, недоступность источника, подстановка fallback.
Вызывающий не знает ни про приоритеты, ни про то, что источник — множество
сущностей.

#### 2.2.2. `domain/topology.py` — снимок топологии и инвариант

```python
@dataclass(frozen=True)
class TopologySnapshot:
    floors: Mapping[FloorId, Floor]
    rooms: Mapping[AreaId, Room]

    def rooms_of(self, floor: FloorId) -> Sequence[Room]: ...
    def aggregate_area_of(self, floor: FloorId) -> AreaId | None: ...

def evaluate_area(light_entities: Sequence[str]) -> AreaStatus: ...
```

**Интерфейс.** Неизменяемый снимок: этажи, помещения, тип помещения, признак
opt-out, статус инварианта, принадлежность помещения этажу, агрегатная Area
этажа. Снимок строится адаптером из реестров; сам модуль о `hass` не знает.
`AreaStatus` — `OK` либо причина отказа (`NO_LIGHT`, `MULTIPLE_LIGHTS`).

**Глубина.** Прячет разнородность реестров Home Assistant (три реестра плюс
метки) за одной структурой и отвечает на вопросы каскада напрямую. Инвариант
§3.3 ТЗ — одна функция, которая тестируется списком строк.

> **Этап 12 — инвариант по метке `ba_area_light`.** Адаптер отбирает световые
> сущности Area **с меткой** `ba_area_light` и зовёт `evaluate_area` по ним:
> ровно одна → `OK`, её `entity_id` идёт в `Room.light_entity_id` (для агрегата
> этажа — `Floor.light_entity_id`); 0 → `NO_LIGHT`, ≥2 → `MULTIPLE_LIGHTS`.
> Непомеченный свет игнорируется — в Area можно держать любые светильники.
> Контракт генератора: [`docs/contracts/contract-ha-lighting-compilers.md`](docs/contracts/contract-ha-lighting-compilers.md) §8.

#### 2.2.3. `domain/profiles.py` — разрешение профилей

```python
def resolve_actions(
    config: Config,
    topology: TopologySnapshot,
    mode: ScheduleMode,
) -> Mapping[AreaId, ActionSet]: ...
```

**Интерфейс.** Возвращает эффективный набор действий для **каждого** помещения с
учётом наследования Объект → Этаж → Помещение и назначения по метке типа.
Помещение без явной настройки получает унаследованный набор; пустой набор —
допустимый результат (ничего не делать).

**Приоритет источников** (от старшего к младшему): профиль помещения → профиль
типа помещения → профиль этажа → профиль объекта.

**Глубина.** Четыре уровня приоритета и обход дерева скрыты за одним вызовом.
Вызывающий получает плоское отображение и больше не думает о наследовании.

#### 2.2.4. `domain/cascade.py` — планировщик каскада

```python
def plan_cascade(
    topology: TopologySnapshot,
    actions: Mapping[AreaId, ActionSet],
    control: ControlState,
    orphaned_area_ids: Iterable[AreaId] = (),
) -> CascadePlan: ...
```

`orphaned_area_ids` — area из конфигурации, отсутствующие в снимке (осиротевшие
профили, §3.7 ТЗ). Вычисляет вызывающий (`config.actions_by_area` минус
`topology.rooms`); попадают в отчёт с причиной `ORPHANED`. В обход помещений не
входят, потому что их нет в топологии.

**Интерфейс.** Возвращает `CascadePlan` — кортеж команд `(target_area_id,
action)` плюс отчёт о пропущенных помещениях с причинами (`OPT_OUT`,
`FLOOR_MANUAL`, `BUILDING_MANUAL`, `INVARIANT_BROKEN`, `ORPHANED`). План
**гарантирует**: команда родительской и дочерней Area в **световом потоке** не
встречается (см. ниже); каждое помещение попадает либо в команду, либо в отчёт о
пропуске — третьего не дано.

**Два потока (этап 11).** Действия делятся на два класса. Свет (`light`/`switch`)
схлопывается в агрегатную Area этажа. Автояркость соседней интеграции
(`arvid_dali_center.set_autobrightness`, предикат `types.is_room_pinned`) адресует
датчики помещения — агрегатной цели у неё нет, поэтому она **всегда** исполняется
по Area помещения и в проверке однородности света не участвует (однородность
считается по набору без room-pinned действий). На однородном этаже команда света
на агрегатную Area может соседствовать с командами автояркости по помещениям: это
разные устройства (групповой свет против датчиков), двойного воздействия на свет
нет.

**Глубина.** Здесь живёт схлопывание, пропуски и вся защита шины DALI. Это самый
глубокий модуль: маленький интерфейс, за которым правило однородности, обход
двух уровней, разделение потоков и причины пропуска.

**Порядок проверки причин пропуска фиксирован** (первая сработавшая побеждает):

```
BUILDING_MANUAL → FLOOR_MANUAL → OPT_OUT → ORPHANED → INVARIANT_BROKEN
```

`ORPHANED` в этом порядке применяется к **сиротам** (area вне снимка,
`orphaned_area_ids`) и с прочими причинами не пересекается — помещения снимка её
не получают. `OPT_OUT` проверяется **до** инварианта намеренно: opt-out — сознательное
исключение помещения из управления, команды по нему всё равно не будет.
Проверять для него инвариант незачем, а пометка `INVARIANT_BROKEN` на исключённом
помещении была бы ложной аварией. Пример: в Area актового зала (он под opt-out)
инженер оставил две световые сущности — это не должно всплывать в мониторинге как
ошибка каскада, которого по залу и так нет. При обратном порядке ложные аварии
на исключённых помещениях зашумили бы мониторинг, топя настоящие нарушения.

**Инвариант плана проверяется тестом**, а не глазами: для любого входа целевые
Area **светового потока** не содержат одновременно агрегатную Area этажа и Area
его помещения. Автояркость всегда по помещению и в этом инварианте не участвует.

> **Этап 12 — цель светового потока = сущность.** Свет целится не по `area_id`, а
> по **помеченной** световой сущности (`Room.light_entity_id`; при схлопывании —
> `Floor.light_entity_id`). `Command` несёт `target` + `target_kind`
> (`ENTITY` — свет / `AREA` — автояркость), исполнитель диспетчеризует по
> `entity_id` либо `area_id`. Так в Area можно держать любой свет, целится только
> помеченный.

#### 2.2.5. `domain/machine.py` — машина состояний

```python
def decide(
    state: OrchestratorState,
    inp: Input,
    now: Instant,
) -> Decision: ...
```

**Интерфейс.** Единственная точка, где живёт политика «что делать сейчас».

- `Input` — `ScheduleChanged | TimerFired | Started | ControlModeChanged`
  (реализовано в `types.py`). Изменение реестра и `reapply` обрабатывает
  **оболочка**: координатор пересобирает снимок топологии и вызывает `decide` с
  обычным входом — отдельных вариантов `RegistryChanged`/`ReapplyRequested` в
  ядре нет.
- `Decision` — новое состояние, план каскада (или его отсутствие), операция с
  таймером (`SetTimer(apply_at, target_mode) | CancelTimer | NoTimerOp`; `apply_at`
  — **абсолютный** момент `now + delay`, не задержка), кортеж доменных событий,
  значения гейтов по этажам.
- **Время передаётся явно** параметром `now` — функция детерминирована и не
  зависит от системных часов.

**Глубина.** За одним вызовом: применять ли каскад немедленно, откладывать ли,
отменять ли отложенный переход, что делать на старте при совпадении и при
расхождении, как ведёт себя Ручной режим здания и этажа, какие события
публиковать.

**Возврат в Автоматический догоняет расписание.** Применяется `schedule_mode`
(текущий вычисленный), а не `applied_mode` (последний применённый до Ручного):
«Авто» означает следовать расписанию, поэтому уход расписания за время Ручного
должен быть подхвачен сразу, а не ждать следующего тика. Расписание вычисляется
и в Ручном (§3.2 ТЗ), так что на момент возврата `schedule_mode` актуален. Ровно одна задержка на здание (решение §7.4) означает, что в
состоянии не более одного отложенного перехода — это резко упрощает и код, и
матрицу тестов.

#### 2.2.6. `domain/storage_schema.py` — схема хранилища

```python
def migrate(major: int, minor: int, data: RawConfig) -> RawConfig: ...
def load_config(raw: RawConfig) -> Config: ...
def dump_config(config: Config) -> RawConfig: ...
```

**Интерфейс.** Чистые преобразования данных. `load_config` считает вход
**недоверенным** и либо возвращает валидную конфигурацию, либо бросает
`ConfigValidationError` с указанием места.

**Глубина.** Миграции и валидация — единственное место, знающее о формате
хранения. Обёртка `Store` в оболочке этих функций не дублирует.

Это делает **миграцию тестируемой** без `hass`, что при отказе от пакета
`homeassistant` иначе было бы невозможно.

### 2.3. Адаптеры (оболочка)

Каждый адаптер — **шов**: место, где поведение подменяется без правки ядра. В
тестах ядра адаптеры не нужны вовсе, потому что ядро принимает и возвращает
данные.

| Адаптер | Роль | Что скрывает |
|---|---|---|
| `adapters/registry.py` | реестры → `TopologySnapshot` | три реестра HA, метки, вычисление статуса Area |
| `adapters/schedule.py` | сущности `event_schedule` → `ScheduleEvent` | фильтрация по атрибуту, `unavailable` |
| `adapters/executor.py` | `CascadePlan` → сервисные вызовы | целеуказание по `area_id`, изоляция сбоев |
| `adapters/timers.py` | `TimerOp` → `async_call_later` | отмена, привязка к жизненному циклу entry |
| `adapters/store.py` | `Store` + `storage_schema` | версии, `async_delay_save` |
| `adapters/publisher.py` | доменные события → шина, состояния → сущности | форматы payload |

**Один адаптер — гипотетический шов, два — настоящий.** Сейчас у каждого шва по
одному адаптеру плюс фейк в тестах ядра — этого достаточно, чтобы шов был
реальным, а не декоративным.

### 2.4. Направление зависимостей

```
sensor/binary_sensor/select/switch  websocket_api.py  __init__.py
        └───────────────┬────────────────────┘
               ▼
         coordinator.py          ← оболочка: собирает снимки, исполняет решения
               │
        ┌──────┴──────┐
        ▼             ▼
    adapters/      domain/       ← ядро: ничего не знает ни о ком
```

**Правило:** `domain/` не импортирует ни `homeassistant`, ни `adapters/`, ни
`custom_components`. Проверяется **тестом-сторожем**, который разбирает AST всех
модулей `domain/` и падает на запрещённом импорте. Критерий неподделываемый:
обойти его можно только сломав тест, что видно в диффе.

```
├── config_flow.py
├── websocket_api.py        # атомарные операции панели
├── domain/                 # ЯДРО — без hass, покрыто тестами
│   ├── types.py            # ScheduleMode, Action, Config, состояние
│   ├── schedule.py
│   ├── topology.py
│   ├── profiles.py
│   ├── cascade.py
│   ├── machine.py
│   └── storage_schema.py
├── adapters/               # ОБОЛОЧКА — швы к HA
│   ├── registry.py
│   ├── schedule.py
│   ├── executor.py
│   ├── timers.py
│   ├── store.py
│   └── publisher.py
│   # ПЛАТФОРМЫ сущностей — в КОРНЕ пакета: HA грузит их как
│   # <интеграция>/<platform>.py, подпапку loader не сканирует.
├── select.py               # режим управления здания: Авто / Ручной
├── switch.py               # режим управления этажа: тумблер, ON = автоматика

├── domain/                 # основное покрытие

```

> **Платформы в корне, не в `entities/`.** Ранняя раскладка помещала их в
> `entities/`; Home Assistant так их не находит — loader ищет платформу по пути
> `custom_components/<домен>/<платформа>.py`. Исправлено на этапе 1b.

### 2.6. Внешние контракты (этапы 7–11)

Всё, на что опираются панель (этап 9) и смежные проекты. Имена — в `const.py`.

**Команды WebSocket** (`websocket_api.py`, префикс `building_automation/`):

| Команда | Права | Вход | Результат |
|---|---|---|---|
| `get_state` | любой | — | мониторинг: `building_control`, `schedule_source[]`, `schedule_mode`, `applied_mode`, `source_available`, `pending`, `floors[]` (`control`, `gate`, `aggregate_area_id`), `rooms[]` (`room_type`, `opt_out`, `status`, `autobrightness`), `last_plan` (`commands[]` с `target`/`target_kind`/`level`, `skipped[]`, `collapse`, `previous_mode`, `applied_mode`), `orphaned`, `autobrightness_entities[]` |
| `get_config` | любой | — | `{config}` — вывод `dump_config` (вкл. `opted_out_areas`) |
| `set_control_mode` | любой | `target` (`building`/`floor`), `mode` (`auto`/`manual`), `floor_id?` | `{ok}` |
| `set_mode_settings` | **admin** | `mode`, `delay_seconds`, `sensors_allowed`, `sensors_allowed_by_floor?` | `{config}` |
| `set_actions` | **admin** | `scope` (`object`/`floor`/`room_type`/`area`), `key?`, `mode`, `actions[]` | `{config}` |
| `clear_actions` | **admin** | `scope`, `key?`, `mode` | `{config}` |
| `set_opt_out` | **admin** | `area_id`, `opted` (bool) | `{config}` |

**Точечность и идемпотентность (§11.1 ТЗ).** Каждая мутация трогает ровно один
узел (`scope`+`key`+`mode`); read-modify-write сериализован отдельным локом
координатора, поэтому устаревшая вкладка не затирает чужую правку. Повторный
вызов с теми же аргументами даёт то же состояние.

> **`set_actions []` ≠ `clear_actions`.** `profiles._effective` смотрит на
> **наличие** ключа, а не на его пустоту: пустой список — явное «ничего не делать»
> на этом уровне (обрывает наследование), а вернуть наследование можно только
> удалением узла. Поэтому это две разные команды, а не одна.

> **opt-out — политика Оркестратора в `.storage`, не метка реестра** (решение
> Q3=C). Множество `opted_out_areas` правится командой `set_opt_out`; координатор
> накладывает его на снимок топологии (`topology.apply_opt_out`), помещение
> пропускается каскадом с причиной `OPT_OUT`. Генератору метка `ba_optout` не
> нужна.

**Валидация.** Результат мутации прогоняется через `dump_config`→`load_config`,
то есть белый список **пар** (домен, сервис) действует и здесь: `light`/`switch` ×
`turn_on`/`turn_off` и `arvid_dali_center.set_autobrightness` (этап 11; пары, а не
крест — иначе третий домен открыл бы `light.set_autobrightness` и
`arvid_dali_center.turn_on`). Ошибка возвращается кодом `invalid_config` с местом
(`actions.object.off[0].domain`). Поле `data` действия — dict: у `light`+`turn_on`
опционально `brightness_pct`; у `set_autobrightness` обязателен `enabled: bool`,
`toggle` запрещён (неидемпотентен).

> **Индикация автояркости (этап 11).** `get_state` отдаёт по каждому помещению
> `autobrightness` (`on`/`off`/`mixed`/`null`) — сведённое состояние тумблеров
> `switch.il_*` соседней интеграции в Area помещения (адаптер
> `adapters/autobrightness.py`); `autobrightness_entities[]` — их entity_id для
> живого watch в панели. Опознавание по префиксу `il_` — **только показ**;
> управление идёт по `area_id` через сервис и от имён не зависит.

**События на шине** (`publisher.py`): `building_automation_mode_changed`
(`new_mode`, `previous_mode`, `source`), `building_automation_mode_warning`
(`target_mode`, `apply_at`), `building_automation_transition_cancelled`
(`cancelled_mode`). События здания-широкие.

**Сервисы** (`services.yaml`): `building_automation.set_control_mode`
(`target`, `mode`, `floor_id?`) и `building_automation.reapply`.

**Сущности** — по ТЗ §10: `select` режима здания; `sensor` режима расписания и
отложенного перехода (атрибут `apply_at`); `binary_sensor` доступности источника;
на каждый Floor — `switch` автоматики (ON = следует расписанию), `binary_sensor`
гейта и `sensor` применённого режима. Все на одном устройстве «Оркестратор здания».

## 3. Модель данных

### 3.1. Типы ядра

Все — `frozen=True` датаклассы либо `StrEnum`; изменяемых структур в ядре нет.
Неизменяемость нужна, чтобы `decide` был повторяем в тестах. `Action`/`ActionSet`
**нехешируемы** (в `data` могут быть списки), поэтому однородность каскада
определяется JSON-ключом, а не хешем (§4.1).

Ниже — ключевые типы; полный список из ~34 объявлений — в `domain/types.py`.
Типы машины состояний (`OrchestratorState`, входы `Input`, `TimerOp`,
`DomainEvent`, `Decision`) — в §3.1.1.

```python
type FloorId = str                  # id этажа (Floor) из реестра HA
type AreaId = str                   # id помещения (Area) из реестра HA

class ScheduleMode(StrEnum):        # lesson | break | off | window
class ControlMode(StrEnum):         # auto | manual — уровень здания
class FloorControl(StrEnum):        # by_building | manual — уровень этажа
class RoomType(StrEnum):            # class | korridor | recreation | zal | special | hall
class SkipReason(StrEnum):          # opt_out | floor_manual | building_manual
                                    # | invariant_broken | orphaned
class AreaStatus(StrEnum):          # ok | no_light | multiple_lights
                                    # (no_light и multiple_lights → SkipReason.invariant_broken)

@dataclass(frozen=True)
class Action:                       # домен ограничен light|switch, сервис — turn_on|turn_off
    domain: str
    service: str
    data: Mapping[str, Any]         # для light.turn_on — brightness_pct и т.п.

type ActionSet = tuple[Action, ...] # кортеж; однородность — по JSON-ключу (§4.1)

@dataclass(frozen=True)
class ControlState:                 # снимок режима управления, вход plan_cascade
    building: ControlMode
    floors: Mapping[FloorId, FloorControl]

@dataclass(frozen=True)
class ModeSettings:                 # настройки режима — область действия «здание»
    delay_seconds: int
    sensors_allowed: bool
    sensors_allowed_by_floor: Mapping[FloorId, bool]   # переопределение

@dataclass(frozen=True)
class Config:
    modes: Mapping[ScheduleMode, ModeSettings]
    actions_object: Mapping[ScheduleMode, ActionSet]
    actions_by_floor: Mapping[tuple[FloorId, ScheduleMode], ActionSet]
    actions_by_room_type: Mapping[tuple[RoomType, ScheduleMode], ActionSet]
    actions_by_area: Mapping[tuple[AreaId, ScheduleMode], ActionSet]
    fallback_mode: ScheduleMode
    opted_out_areas: frozenset[AreaId]  # исключённые из управления (Q3=C)
```

Прочие типы данных: `Floor`, `Room` (§2.2.2), `ScheduleEvent`, `ScheduleResolution`
(§2.2.1), `Command`, `SkipEntry`, `CascadePlan` (§2.2.4).

### 3.1.1. Типы машины состояний

```python
type Instant = float                # монотонное время в секундах (параметр now)

class EventSource(StrEnum):         # schedule | manual (manual — резерв, см. §7)

@dataclass(frozen=True)
class PendingTransition:            # target_mode, apply_at
@dataclass(frozen=True)
class OrchestratorState:            # полный вход/выход decide
    config: Config
    topology: TopologySnapshot
    control: ControlState
    schedule_mode: ScheduleMode
    source_available: bool
    applied_mode: ScheduleMode | None   # None = ничего не применено (до старта)
    pending: PendingTransition | None

# Входы (union): ScheduleChanged(resolution) | TimerFired | Started(resolution)
#              | ControlModeChanged(building?, floor_id?, floor_control?)
# TimerOp:     NoTimerOp | SetTimer(apply_at, target_mode) | CancelTimer
# DomainEvent: ModeChanged(new_mode, previous_mode, source)
#            | ModeWarning(target_mode, apply_at) | TransitionCancelled(cancelled_mode)

@dataclass(frozen=True)
class Decision:
    state: OrchestratorState
    plan: CascadePlan | None
    timer_op: TimerOp
    events: tuple[DomainEvent, ...]
    gates: Mapping[FloorId, bool]
```

### 3.2. Схема хранилища

В `.storage` пишется только конфигурация (профили и настройки режимов).
Топология, имена и состав помещений не дублируются — они в реестре.

Конверт `version`/`minor_version`/`data` добавляет обёртка `Store` (adapters/store.py);
ядро (`dump_config`/`load_config`) оперирует **только содержимым `data`**.

```jsonc
{
  "version": 1,          // ← конверт Store
  "minor_version": 1,    // ← конверт Store
  "data": {              // ← это возвращает/принимает dump_config/load_config
    "fallback_mode": "off",
    "modes": {
      "lesson": { "delay_seconds": 300, "sensors_allowed": true,
                  "sensors_allowed_by_floor": { "<floor_id>": false } },
      "break":  { "delay_seconds": 0,   "sensors_allowed": false,
                  "sensors_allowed_by_floor": {} }
    },
    "actions": {
      "object":    { "<mode>": [ {"domain":"light","service":"turn_off","data":{}} ] },
      "floor":     { "<floor_id>": { "<mode>": [ ... ] } },
      "room_type": { "korridor":   { "<mode>": [ ... ] } },
      "area":      { "<area_id>":  { "<mode>": [ ... ] } }
    },
    "opted_out_areas": [ "<area_id>", ... ]   // opt-out политика (Q3=C)
  }
}
```

Ключи — `floor_id` и `area_id` из реестра: они стабильны при переименовании.
Записи с исчезнувшими ключами **сохраняются** и помечаются осиротевшими.

## 4. Алгоритмы и сложность

Обозначения: `A` — помещений (20–50), `F` — этажей (5), `S` — сущностей
расписания (единицы), `E` — всего сущностей в Home Assistant (тысячи),
`L` — световых сущностей.

| Операция | Время | Память | Когда выполняется |
|---|---|---|---|
| `resolve_schedule_mode` | O(S) | O(1) | на каждое изменение расписания |
| Сборка `TopologySnapshot` | O(E) | O(A + L) | только на изменение реестра |
| `resolve_actions` | O(A) | O(A) | на каждую смену режима |
| `plan_cascade` | O(F·A) | O(A) | на каждое применение (F=этажей, константа) |
| `decide` | O(1) сверх вызовов выше | O(1) | на каждый вход |

**Итого на звонок — O(A)**, при A ≤ 50 это микросекунды. Дорогая операция
здесь только сборка снимка топологии, O(E) по реестру сущностей; она вынесена из
горячего пути и выполняется по событию изменения реестра, а не по звонку.

### 4.1. Схлопывание за O(A)

Наивная реализация сравнивала бы помещения этажа попарно — O(A²). Вместо этого
однородность этажа проверяется за один проход по **каноничному ключу** набора
(JSON-представление `[[domain, service, data], …]` с `sort_keys`): складываем
ключи помещений этажа в множество, если его мощность равна единице и пропусков
на этаже нет — схлопываем.

> Ключ — JSON, а не хеш `ActionSet`: `Action.data` может содержать списки
> (например `rgb_color`) и нехешируем. JSON-канон даёт O(A) без требования
> хешируемости и не зависит от порядка ключей `data`.

```
для каждого этажа:
    наборы ← { actions[area] | area ∈ помещения этажа, не пропущено }
    если пропусков нет и |наборы| == 1 → одна команда на агрегатную Area
    иначе                              → команда на каждое непропущенное помещение
```

Именно ради этого действия хранятся кортежами, а не списками: список нехешируем,
и группировка деградировала бы до попарного сравнения.

### 4.2. Выбор структур данных

- **Отображения по `area_id` / `floor_id`** — доступ O(1); при обходе каскада
  выполняется A обращений, любая другая структура дала бы худшую константу без
  выигрыша.
- **Неизменяемые снимки** вместо ссылок на реестр — ядро остаётся чистым, а
  повторный вызов `decide` на тех же данных даёт тот же результат, что и есть
  условие воспроизводимости тестов. (`Action` при этом нехешируем — однородность
  каскада идёт по JSON-ключу, §4.1.)
- **Один отложенный переход** (следствие решения §7.4) хранится как поле
  состояния, а не как коллекция таймеров: отмена — присваивание, а не обход.

## 6. Количественные критерии

Пороги подобраны с учётом того, что покрывается **только ядро**; для него
требования выше обычных, поскольку это единственная автоматически проверяемая
часть.

| Критерий | Порог | Как измеряется |
|---|---|---|
| Покрытие ветвей `domain/` | **≥ 95 %** | `pytest --cov=custom_components/building_automation/domain --cov-branch` |
| Mutation score `machine.py`, `cascade.py`, `schedule.py`, `profiles.py` | **≥ 70 %** | `mutmut run` |
| Ошибки линтера | **0** | `ruff check` |
| Ошибки типов | **0** | `mypy --strict` |
| Диффы форматтера | **0** | `ruff format --check`, `prettier --check` |
| Импорты HA в `domain/` | **0** | тест-сторож §5.7 |
| Планирование каскада на 50 помещений | **< 5 мс** | тест с замером |
| BDD-сценарии без теста | **0** | сверка §5 с именами тестов |
| Пропуски тестов без обоснования | **0** | `--strict-markers`, комментарий у каждого `skip` |

**Почему их нельзя «обмануть».** Покрытие меряется по ветвям и только по `domain/`
— добавить непокрытый код в адаптеры и разбавить метрику не выйдет. Mutation
score ловит тесты, которые исполняют код, но ничего не проверяют. Сторож импортов
нельзя обойти, не сломав сам тест, что видно в диффе. Порог по времени
измеряется на сгенерированной топологии в 50 помещений, а не на игрушечной.

**Что этими критериями не проверяется** — HA-обвязка целиком: регистрация
сущностей, `config_flow`, WebSocket, жизненный цикл entry, фактическая запись в
`Store`, блокирующие вызовы. Перечень и ручной чек-лист — `.ai/rules/tooling.md`
§5. Это принятая цена отказа от пакета `homeassistant`, а не упущение.

## 7. Обоснование решений

### 7.1. Функциональное ядро вместо тестов с `pytest-homeassistant-custom-component`

**Выбрано:** чистое ядро без `hass`, обвязка непокрыта.
**Отвергнуто:** PHACC — даёт покрытие обвязки, но тянет пакет `homeassistant`,
от чего отказались по решению владельца; и требует держать пин PHACC в
синхронизации с версией HA.
**Цена:** обвязка проверяется только ревью и полевым тестом.
**Смягчение:** обвязка сведена к минимуму, вся политика — в ядре.

### 7.2. Целеуказание по `area_id`, а не по `entity_id`

**Выбрано:** цель команды — `area_id`, при политике «в Area ровно одна световая
сущность».
**Отвергнуто:** хранение `entity_id` группового светильника — у YAML-групп
`unique_id` не равен `entity_id`, а переименование группы оставляет прежний
идентификатор; ссылка разъезжается молча.
**Отвергнуто:** назначение групп в Area **вместе** с лампами — тогда сервисный
вызов по Area обошёл бы и группу, и каждую лампу, удвоив трафик DALI для всех
потребителей, включая дашборд.
**Цена:** инвариант, который Home Assistant не охраняет.
**Смягчение:** рантайм-проверка §2.2.2, отказ от каскада по нарушенной Area.

### 7.3. Гейт-условие вместо `automation.turn_on/off`

**Выбрано:** Оркестратор публикует `binary_sensor` на этаж, blueprint проверяет
его условием «не равно `off`».
**Отвергнуто:** переключение автоматизаций — включённость автоматизации это
второе персистентное состояние, способное разойтись с режимом после перезапуска;
выключенная автоматизация не оставляет трейсов, и причина «почему не сработало»
на объекте не видна.
**Цена:** правка шаблонов blueprint в смежном проекте.
**Fail-open** обязателен: недоступный гейт разрешает работу, иначе сбой
интеграции оставит здание без света.

**Форма условия — `condition: template`**, `{{ states(<гейт>) != 'off' }}`.
Первоначально спецификация требовала `condition: state` как более дешёвый; это
оказалось ошибкой, вскрытой смежным проектом и подтверждённой проверкой по
исходникам HA 2026.5.4: на **несуществующей** сущности `condition: state` бросает
`ConditionErrorMessage`, `not` её не проглатывает, и автоматизация не
выполняется. То есть конструкция давала fail-**closed** ровно тогда, когда
Оркестратор не установлен или перезагружается — весь объект остался бы без света
по датчикам. `has_value()` в шаблоне непригоден по той же причине.

Принятая обратная сторона: опечатка в имени гейта не даст ошибки, условие станет
всегда истинным, и режимы перестанут влиять на датчики молча. Тяжесть
несопоставима с темнотой во всём здании, а имя подставляется генератором по
формуле и руками не вводится.

### 7.4. Одна задержка на режим и на всё здание

**Выбрано:** задержка — свойство режима, область действия «здание».
**Отвергнуто:** задержка в профиле с наследованием до помещения — дало бы до
`A` одновременных отложенных переходов, набор независимых таймеров, зависимость
схлопывания ещё и от совпадения задержек и комбинаторный рост матрицы тестов.
**Обоснование:** в legacy задержка была одна (`input_number.urok_time_delay`);
потребности в разных задержках не заявлено. Следствие — в состоянии не более
одного отложенного перехода, отмена сводится к присваиванию.

### 7.5. Флаг «датчики разрешены» с переопределением на этаже

**Выбрано:** свойство режима, переопределяемое на этаже.
**Отвергнуто:** наследование до помещения — гейт публикуется на этаж, и
помещенческое значение было бы невыразимо; модель допускала бы то, что система
не может исполнить.
**Отвергнуто:** гейт на каждое помещение — 20–50 сущностей вместо 5 и привязка
каждого blueprint к своей.

### 7.6. Схлопывание по совпадению набора действий

**Выбрано:** однородность = совпадение `ActionSet` по каноничному JSON-ключу
(`Action` нехешируем — в `data` бывают списки; хеш неприменим).
**Отвергнуто:** попарное сравнение помещений — O(A²) без выигрыша.
**Отвергнуто:** учитывать в однородности ещё и задержку — не требуется, задержка
общая на здание (§7.4).

### 7.7. Явная передача времени в `decide`

**Выбрано:** `now: Instant` — параметр.
**Отвергнуто:** чтение системных часов внутри — сделало бы функцию
недетерминированной и потребовало бы подмены времени в каждом тесте.

---

### 7.8. Технические помещения вне управления по расписанию

**Выбрано:** групповой светильник тех.помещений этажа (`light.tekh_pom_<N>_i_etazh`)
ни в какую Area не назначается, Оркестратор им не управляет.

**Контекст:** у технических помещений **нет собственных Area** в реестре — группа
`tekh_pom` агрегирует помещения, отдельными Area не представленные. Поэтому
Оркестратор их попросту не видит: ни целью каскада они не становятся, ни инвариант
по ним не проверяется.
**Отвергнуто:** положить группу тех.помещений в агрегатную Area этажа — там
оказалось бы две световые сущности, инвариант §7.2 сломался бы.
**Отвергнуто:** завести для группы отдельную Area — лишняя агрегатная сущность со
своим инвариантом ради помещений, которыми по расписанию управлять не требуется.
**Цена:** свет в технических помещениях не гасится автоматически; это
эксплуатационная зона ответственности человека.

Метка opt-out для технических помещений **не нужна**: раз Area нет, помечать
нечего. Ранняя редакция ошибочно её предписывала — требование снято.
