# HANDOFF — управление автояркостью из сторонней интеграции

> Для разработчика соседней интеграции в том же Home Assistant (или внешнего клиента): как
> включать/выключать автояркость и задавать окна работы датчиков. Знать наш протокол и шину не
> нужно. Описание сервисов изнутри — [SERVICES.md](SERVICES.md).

---

## 1. Что доступно снаружи

| Сервис | Что делает |
|---|---|
| `arvid_dali_center.set_autobrightness` | включить/выключить автояркость у датчиков цели |
| `arvid_dali_center.set_effective_time` | окна времени, когда датчик управляет светом |

Опираться стоит только на них. У нас есть ещё WebSocket-команды, но они адресуются шлюзом,
каналом и адресом устройства, требуют админа и меняются вместе с внутренностями — контрактом для
внешнего кода не являются.

## 2. Права: при чём тут `require_admin`

`require_admin` — это ограничение HA на **WebSocket-команде**, и проверяет оно флаг «администратор»
у **пользователя**, чьим токеном открыто соединение. Оно про пользователя, а не про интеграцию:
у интеграции «прав» в этом смысле нет.

| Как вызываете | Что проверяется |
|---|---|
| Ваш код в этом же HA (`hass.services.async_call`) | ничего — у внутреннего вызова пользователя нет вообще |
| Автоматизация или скрипт HA | то же, ничего |
| Снаружи по WS/REST с токеном | пользователь, которому принадлежит токен |

**Наши сервисы админа не требуют** — они зарегистрированы как обычные, их зовёт и не-админ.
Админ нужен только для наших WS-команд, а они вам и не нужны (§1).

Практически: если ваша интеграция — компонент в этом же HA, вы просто зовёте сервис, и настраивать
ничего не надо. Токен нужен, только если вы ходите в HA снаружи; долгоживущий токен наследует
права создавшего его пользователя.

## 3. `set_autobrightness`

**Что это по сути:** включение/выключение **функции датчика освещённости**. Датчик перестаёт
управлять светом — и только. Настройка автояркости остаётся на контроллере, поэтому возврат — тот
же вызов с `enabled: true`, мгновенно и без нагрузки на шину.

⛔ **Удаления настройки в этом контракте нет** — ни этим сервисом, ни любым другим снаружи.
Операция, после которой автояркость нельзя вернуть тем же вызовом, чужому коду не выдаётся.

**Поля** — нужно указать `enabled` **или** `toggle`:

| Поле | Тип | Смысл |
|---|---|---|
| `enabled` | bool | `true` — датчик управляет светом, `false` — нет |
| `toggle` | bool | инвертировать (для одной клавиши «вкл/выкл») |

При `toggle` на нескольких датчиках результат предсказуем: если включён хоть один — выключается
вся цель, иначе включается вся.

Выключенное состояние **переживает перезагрузку HA**: то, что выключено осознанно, при старте
обратно не будится.

**Ответ** (запрашивается явно — `return_response`):

```json
{ "changed": 3, "total": 4,
  "results": [ {"gw": "E22435088727", "address": 3, "devSn": "…", "ok": true, "error": null} ] }
```

## 4. Кого именно выключаем — адресация

Цель задаётся штатным `target` HA. Четыре способа, от точечного к массовому:

| Способ | Как | Когда |
|---|---|---|
| **Одна сущность** | `entity_id: sensor.il_kab301_1` | точечно, один датчик |
| **Устройство** | `device_id: <id устройства>` | точечно, надёжнее всего (см. ловушку 2) |
| **Пространство** | `area_id: kabinet_301` | всё помещение |
| **Этаж / метка** | `floor_id`, `label_id` | этаж, произвольная выборка |

Да, при `area_id` датчики ищет сам HA: он раскрывает область до устройств и сущностей, а сервис
уже отбирает из них датчики освещённости. Перечислять устройства руками не нужно. Списком тоже
можно: `entity_id: [sensor.il_kab301_1, sensor.il_kab301_2]`.

**Лишнее в цели отсеивается само.** Лампы, группы, панели, зомби и осиротевшие записи
игнорируются — можно смело кидать целую область. Если подходящих датчиков не нашлось, сервис
вернёт `{"changed": 0, "results": [], "warning": "в цели нет датчиков освещённости (0202)"}` и
напишет предупреждение в журнал: молчаливого «успеха» не будет.

⚠ **Ловушка 1 — область должна быть проставлена.** Мы НЕ назначаем помещения автоматически: пока
датчики не разложены по областям руками, адресация `area_id` найдёт ноль устройств (в ответе
будет `changed: 0` и то самое предупреждение). Если не уверены — адресуйтесь точечно.

⚠ **Ловушка 2 — берите сущность освещённости, а не движения.** Датчик движения и датчик
освещённости — одно устройство HA, но для контроллера это две разные сущности шины. Автояркость
живёт на освещённости, поэтому цель из одной только `ms_*` (движение) даст ноль результатов.
Подходят: `il_*` (люкс), её тумблер `*_act`, либо `device_id` устройства — тогда HA раскроет его
целиком и нужное попадёт в выборку само. **`device_id` — самый безопасный точечный вариант.**

## 5. Примеры

**Из своей интеграции (тот же HA):**

```python
report = await hass.services.async_call(
    "arvid_dali_center", "set_autobrightness",
    {"enabled": False},                    # или {"toggle": True}
    target={"device_id": device_id},       # или {"area_id": "kabinet_301"}
    blocking=True, return_response=True,   # return_response требует blocking=True
)
if report["changed"] < report["total"]:
    _LOGGER.warning("автояркость применена не везде: %s", report["results"])
```

**Из автоматизации по расписанию:**

```yaml
automation:
  - alias: Ночью автояркость не нужна
    trigger:
      - platform: time
        at: "22:00:00"
    action:
      - service: arvid_dali_center.set_autobrightness
        target:
          area_id: kabinet_301
        data:
          enabled: false
        response_variable: report
```

**Снаружи по WebSocket:**

```json
{ "id": 5, "type": "call_service",
  "domain": "arvid_dali_center", "service": "set_autobrightness",
  "target": {"entity_id": "sensor.il_kab301_1"},
  "service_data": {"enabled": false},
  "return_response": true }
```

REST — то же: `POST /api/services/arvid_dali_center/set_autobrightness` с заголовком
`Authorization: Bearer <token>`; для отчёта добавьте `?return_response`.

## 6. Как прочитать текущее состояние

У датчика освещённости есть сущность-тумблер `switch.*`: `on` — автояркость работает, `off` —
приостановлена. Он обновляется и когда состояние сменил наш сервис, и когда его сменили из нашей
карточки — источник один.

Имена не парсите (у именованного датчика тумблер `<имя>_act`, у безымянного —
`<тип>_<адрес>_<sn5>_active`): ищите сущности устройства через реестры HA. Для ОДНОГО датчика
`switch.turn_on/off` делает ровно то же, что сервис.

## 7. `set_effective_time` — расписание НА ШЛЮЗЕ

Окна времени, в которые датчик управляет светом, исполняет сам контроллер — работает, даже если
HA выключен.

| Поле | Тип | Смысл |
|---|---|---|
| `windows` | список строк | `["08:00-13:00", "14:00-17:30"]` — вне окон датчик не управляет светом |
| `function` | `autobrightness` (по умолч.) / `motion` / `both` | какой функции задаём |
| `clear` | bool | `true` — убрать ОКНА (круглосуточно); `windows` игнорируется |
| `pace` | float 0..10 | пауза между устройствами, с (по умолчанию `0.3`) |

Ответ: `{changed, total, windows, warnings, results:[…]}`.

- `clear: true` снимает **только расписание** — сама автояркость остаётся (сервис вычитывает её
  перед записью и возвращает обратно).
- **Окна только внутри суток**: `22:00-06:00` отклоняется, задавайте двумя окнами — так устроено
  железо.
- **Окна исполняет шлюз по своим часам.** Разошлись с HA больше чем на минуту — сервис положит это
  в `warnings`. Проверяйте их: снаружи такое расхождение невидимо.
- Пересечение окон тоже попадает в `warnings` (как его трактует контроллер — не проверено).

## 8. Правила эксплуатации

- **DALI-шина — узкое место.** Массовая запись по этажу её нагружает: отсюда `pace` и отсутствие
  автоматического повтора (повтор = вторая массовая запись на шину). Судите по отчёту
  `changed`/`total`, а не по тому, что вызов не бросил ошибку.
- **Работающая автояркость блокирует создание DALI-групп** (шина занята). Это не наш дефект —
  родной DALI Center ведёт себя так же. Если ваш код создаёт группы: `set_autobrightness
  {enabled: false}` → создать группы → `set_autobrightness {enabled: true}`.
- **Отказы видимые.** Упавший датчик приезжает в `results` с `ok: false` и текстом ошибки.
- **Каждый вызов — реальная запись на шину** по каждому датчику цели. Для частого дёрганья
  инструмент не предназначен.

## 9. Чего в контракте нет

Настройка самого контура (цель-группа, коридор освещённости, режимы) делается в нашей карточке.
Снаружи предполагается управлять уже настроенным контуром. Нужно больше — обсудим отдельный
эндпоинт.
