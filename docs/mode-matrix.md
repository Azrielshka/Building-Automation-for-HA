# Матрица режимов и профили действий

Справочник для пусконаладчика: как устроена вкладка **«Матрица режимов»**, что
над чем главенствует, что делают действия профиля на каждом уровне и как собрать
типовые сценарии настройки.

Термины — по [`CONTEXT.md`](../CONTEXT.md). Механику ядра см. в [`SPEC.md`](../SPEC.md)
(§2.2.3 профили, §2.2.4 каскад).

---

## 1. Два независимых механизма

Панель настраивает **две разные вещи**, их нельзя путать:

| Механизм | Что делает | Гранулярность | Где в панели |
|---|---|---|---|
| **Действия профиля** | сервисные вызовы `light`/`switch` при смене режима | до **помещения** (наследование Объект→Этаж→Тип→Помещение) | «Действия профиля» |
| **Датчики (гейт)** | разрешает/запрещает автоматизации по датчикам движения | только **на этаж** | «Настройки режимов» |

> Датчики — это **не** действие профиля. Нельзя выключить датчики «для типа
> class» или «для одного помещения»: гейт вычисляется на этаж. Свет и розетки —
> можно с точностью до помещения.

---

## 2. Иерархия действий профиля: что над чем главенствует

Для каждого помещения ядро вычисляет **эффективный набор действий** по режиму,
проходя уровни от частного к общему. **Побеждает первый уровень, на котором для
этого режима что-то задано:**

```
Помещение (area)      ← самый частный, главенствует над всеми
   ↓ если не задано
Тип помещения (class, korridor, zal, …)
   ↓ если не задано
Этаж (floor)
   ↓ если не задано
Объект (всё здание)   ← самый общий, применяется по умолчанию
```

Пример: если для режима «Урок» действия заданы и на Объекте, и на Этаже 2, и на
помещении `105_aktovyi_zal` — в зале сработает **профиль помещения**, на
остальных помещениях 2-го этажа — **профиль этажа**, на прочих этажах — **профиль
объекта**.

### Ключевое правило: «задано» ≠ «пусто»

Наследование обрывается по **наличию** узла, а не по его содержимому:

- **«наследует»** — на уровне узла НЕТ (кнопка «Наследовать» / `clear_actions`).
  Помещение берёт действия с вышестоящего уровня.
- **«задано N»** — узел ЕСТЬ, в нём N действий (кнопка «Сохранить» /
  `set_actions`). Даже **«задано 0»** (пустой список) — это осознанное
  **«ничего не делать»**: наследование оборвано, вышестоящие профили НЕ
  применяются.

Поэтому в панели две раздельные кнопки:
- **«Сохранить»** — записать действия узла (в т.ч. пустой список).
- **«Наследовать»** — удалить узел, вернуть наследование сверху.

Строка **«Действует для помещения»** (при выборе Уровень = Помещение) показывает,
какой уровень реально победил по каждому режиму.

## 3. Что такое «действие профиля» и куда оно применяется

Действие профиля — это **сервисный вызов**, нацеленный на **Area целевого
помещения** по `area_id`. Home Assistant разворачивает `area_id` в сущности,
привязанные к этой Area.

**Важно:** уровень (Объект/Этаж/Тип/Помещение) определяет только то, **какие
помещения** получат этот набор действий по наследованию. Сама цель вызова —
всегда Area обрабатываемого помещения. То есть «действие на уровне Этажа» — это не
«одна команда на этаж», а «этот набор действий применить к каждому помещению
этажа» (которые затем могут **схлопнуться**, см. §5).

Разрешены только идемпотентные вызовы из белого списка:

| Домен | Сервисы | Чем управляет в целевой Area |
|---|---|---|
| `light` | `turn_on`, `turn_off` | **групповым светильником помещения** (в Area ровно один световой объект — инвариант). При схлопывании этажа — **групповым светом этажа** (`ves_N`) |
| `switch` | `turn_on`, `turn_off` | **всеми `switch`-сущностями Area** — коммутируемые нагрузки: розетки, реле, питание проектора и т.п. |

`toggle` и другие домены запрещены (валидация ядра отвергнет с указанием места).

### `light` на разных уровнях — что физически включается

Цель всегда одна (свет Area), меняется лишь **охват**:

- **Объект → `light.turn_off`**: во всех помещениях гасится их групповой свет.
  Если этаж однороден (все помещения получили одно и то же) — каскад **схлопнётся**
  в один вызов на групповой свет этажа `ves_N`.
- **Этаж 2 → `light.turn_on`**: включается свет только помещений 2-го этажа.
- **Тип `zal` → `light.turn_on`**: включается свет во всех залах, независимо от
  этажа.
- **Помещение `105_aktovyi_zal` → своё**: только этот зал; его наличие
  **разворачивает** схлопывание этажа (см. §5).

### `switch` — примеры

- **Тип `zal` → `switch.turn_on` в «Уроке»**: включить розетку/реле проектора во
  всех залах на время урока, `switch.turn_off` в «Не рабочее время».
- **Помещение → `switch.turn_off` в «Окошке»**: обесточить конкретную нагрузку.

`switch.turn_on` с `area_id` включает **все** switch-сущности этой Area — если
розеток несколько, сработают все.

## 4. Настройки режимов (задержка и датчики)

Верхняя карточка «Настройки режимов» — по каждому из 4 режимов:

- **Задержка, c** — через сколько секунд после смены режим реально применится
  (отложенный переход, одна задержка на всё здание). `0` — сразу.
- **Датчики (по зданию)** — базовый гейт: включены/выключены автоматизации по
  датчикам движения в этом режиме.
- **Переопределение по этажу** (`насл.` / `вкл` / `выкл`) — точечно для этажа:
  `насл.` — как по зданию; `вкл`/`выкл` — жёстко для этого этажа.

Гейт публикуется сущностью `binary_sensor` на этаж; blueprint датчика читает её
и работает по принципу fail-open (нет сущности — датчики разрешены).

## 5. Схлопывание (почему уровень «Этаж» = групповой свет этажа)

Если **все** помещения этажа получили **одинаковый** набор действий, каскад
сворачивает их в **один** вызов на агрегатную Area этажа (`ves_N`) — управляется
групповой свет этажа. Как только хоть одно помещение этажа **переопределено**
(свой профиль на уровне Помещения/Типа), этаж **разворачивается** в покомнатные
вызовы, а прочие помещения этажа управляются по отдельности.

Уровень схлопывания последнего каскада виден в «Мониторинг → Последний каскад».

## 6. Полное исключение помещения: opt-out

Отдельно от действий: помещение можно **полностью исключить из каскада** — оно
попадает в отчёт с причиной `opt_out`, никакие действия профиля к нему не
применяются.

Это делается **в панели**: Матрица режимов → Действия профиля → Уровень =
**Помещение**, выбрать помещение → галочка **«Исключить помещение из управления
по расписанию (opt-out)»**. Только администратор.

> **opt-out — политика Оркестратора, а не метка реестра** (решение Q3=C). Список
> исключённых помещений хранится в `.storage` Оркестратора, правится панелью, не
> зависит от генератора и не требует метки `ba_optout` в Home Assistant.

Разница с «задано 0»:
- **opt-out** — помещение вообще не участвует в каскаде, помечено «исключено».
- **пустой профиль** (`set_actions []`) — помещение участвует, но команд не
  получает (и разворачивает схлопывание этажа).

## 7. Сценарии настройки

### 7.1. Убрать все помещения типа `class` из управления светом/розетками

Цель: помещения-классы не трогаются профилем ни в одном режиме.

Панель → **Матрица режимов** → **Действия профиля**:
1. Уровень = **Тип помещения**, ключ = **class**.
2. Для **каждого** режима (Урок, Перемена, Окошко, Не рабочее время) нажать
   **«Сохранить»** с **пустым** списком действий (не добавляя ни одной строки).
3. Проверить: у каждого режима состояние стало **«задано 0»** (не «наследует»).

Теперь классы получают пустой профиль на уровне Типа → он главенствует над Этажом
и Объектом → команд свет/switch не будет. (Свет классов останется в том
состоянии, в каком был; профиль его не трогает.)

> Альтернатива для конкретного помещения (а не всего типа): галочка **opt-out**
> для этого помещения (§6) — тогда оно ещё и помечается «исключено» в мониторинге.

### 7.2. Датчики всегда выключены

Цель: автоматизации по датчикам не работают ни в одном режиме.

Панель → **Матрица режимов** → **Настройки режимов**:
- у **всех 4 режимов** снять галочку **«Датчики (по зданию)»**.

Если нужно выключить датчики только на конкретном этаже — в тех же строках
поставить его переопределение в **`выкл`** для всех режимов (остальные этажи —
`насл.`).

> Напоминание: «только для классов» так не сделать — гейт на этаж. Если классы
> сосредоточены на одном этаже, используйте переопределение по этому этажу.

### 7.3. Ваш комбинированный сценарий

«Классы убрать из управления + датчики всегда выключены»:
1. §7.1 — тип `class`, пустой профиль во всех режимах.
2. §7.2 — датчики выкл во всех режимах (по зданию), либо по этажу классов.

### 7.4. Другие типовые настройки

- **Гасить весь объект в «Не рабочее время»**: Уровень = Объект, режим Off →
  `light.turn_off`. Однородные этажи схлопнутся в групповой свет этажей.
- **Один этаж со своим сценарием**: Уровень = Этаж, ключ = нужный этаж → задать
  действия; переопределяет объект только для него.
- **Особое помещение** (зал, серверная): Уровень = Помещение → свой профиль;
  разворачивает схлопывание своего этажа.
- **Проектор в залах**: Уровень = Тип `zal` → `switch.turn_on` в «Уроке»,
  `switch.turn_off` в «Не рабочее время».

## 8. Частые ошибки

- **Путать «наследует» и «задано 0».** Первое — берёт сверху; второе — осознанное
  «ничего не делать», обрывает наследование. Смотрите на состояние строки.
- **Ждать датчики per-room/per-type.** Гейт только на этаж (§1, §4).
- **Ждать, что `light` на уровне Этажа — одна команда «на этаж».** Это набор для
  каждого помещения; в один вызов на `ves_N` он сворачивается только при
  однородности этажа (§5).
- **Забыть про инвариант Area.** Если в Area не ровно один световой объект,
  помещение пропускается (`no_light`/`multiple_lights` в мониторинге) — профиль
  к нему не применяется.
