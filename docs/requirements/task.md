# Название проекта: Интеграция «Building Automation» (Оркестратор здания) для Home Assistant

> Редакция 4 от 2026-07-22. Приведена в соответствие с [`TZ.md`](TZ.md).
> Изменения — в конце документа.

**Концепция:** Создание корневого координатора (Custom Component) для Home Assistant, который настраивается через графический интерфейс и берёт на себя высокоуровневую логику здания — режимы работы, расписания, системные задержки, разрешение и запрет работы нижестоящих систем, — заменяя множество разрозненных YAML-автоматизаций.

**Ключевые правила:**
* Кастомная интеграция для Home Assistant (**Python 3.14.2+** — требование Home Assistant Core 2026.5.4, целевой версии объекта).
* Следование стандартам разработки Home Assistant Core: `ConfigEntry.runtime_data`, `DataUpdateCoordinator`, Event Bus, Device/Entity/Area/Floor Registry, `async_forward_entry_setups`.
* **Топология берётся из реестра Home Assistant**: Этаж = Floor, Помещение = Area; тип помещения и признак исключения из автоматики — метки (Labels). Собственное дерево топологии не ведётся.
* **Политика Area: в Area находится ровно одна сущность домена `light`** — групповой светильник соответствующего уровня (общая группа помещения либо этажная группа). Индивидуальные светильники и зонные группы в Area не помещаются. Датчики и панели в Area остаются — они не относятся к домену `light`.
* Проект рассчитан на **новые объекты**: миграция текущей конфигурации колледжа Химки в задачу не входит.
* Хранение в JSON внутри `.storage` через `homeassistant.helpers.storage.Store` — только профили режимов, по ключам `floor_id` / `area_id`.

**Технологические ограничения, библиотеки, окружение:**
* Никакой генерации промежуточных YAML-файлов или `script.*` / `automation.*` сущностей. Переключение чужих автоматизаций через `automation.turn_on/off` также не используется.
* Взаимодействие с нижестоящими системами — через собственные сущности состояния (источник истины) и Custom Events (уведомление о смене). Прямые импорты, обращения к `hass.data` чужих интеграций и вызовы их сущностей запрещены.
* Действия профилей ограничены доменами **`light` и `switch`**, только идемпотентные `turn_on` / `turn_off`; `toggle` запрещён.
* **Цель действия — `area_id`.** Благодаря политике «одна световая сущность в Area» это разворачивается ровно в одну команду на групповой светильник. Хранится `area_id`, а **не** `entity_id`: у YAML-групп `unique_id` не равен `entity_id`, и переименование группы после деплоя оставляет прежний идентификатор — ссылка на Area устойчивее.
* **Инвариант проверяется в рантайме.** Перед каскадом по Area интеграция считает световые сущности в ней: не ровно одна — Area помечается как ошибка конфигурации и каскад по ней не выполняется. Молча дублировать команды на шине DALI недопустимо.
* UI-часть (Custom Panel) — vanilla JS + Lit без шага сборки, интеграция через WebSocket API Home Assistant.

**Развёрнутое описание проекта и его целей:** Интеграция разрабатывается для инженеров-пусконаладчиков, чтобы дать им инструмент настройки здания (колледжа/школы) без написания YAML.

**Что делаем:** Разрабатываем ядро (Python), которое читает внешний источник расписания, вычисляет режим работы объекта (машина состояний), каскадно применяет «Профили режимов» с наследованием Здание → Этаж → Помещение и разрешает либо запрещает работу автоматизаций по датчикам движения. Это включает отсчёт системных задержек, сервисные вызовы к групповым светильникам и публикацию состояния и событий. Также создаём Custom Panel для визуальной настройки.

**Место в существующей системе:** Рядом работают генератор конфигов `ha-lighting-compilers` (создаёт групповые светильники, Areas, Floors, скрипты, автоматизации и blueprint'ы) и система управления по датчикам движения `zone_manager`. Слой режимов работы здания в них не реализован — есть только пустые `input_boolean.regim_auto_<N>` и ручная обвязка из четырёх YAML-автоматизаций. Оркестратор занимает эту нишу и упраздняет обвязку.

**Разграничение и порядок внедрения:** Генератор владеет всем, что выводится из проекта (Excel): Floors, Areas, групповые светильники и их назначение в Areas, метки типа помещения, метка агрегатной Area этажа, гейт-условие в шаблонах blueprint. Оркестратор владеет тем, что вычисляется в рантайме: сущности режимов и гейта, профили, проверка инварианта. **Генератор разворачивается первым** — на новом объекте Оркестратору не на что опереться. Гейт-условие можно выкатывать вместе с генератором, до появления Оркестратора: несуществующая сущность даёт `unknown`, условие её пропускает.

**Границы (что НЕ входит в задачу):**
* НЕ работает с протоколами оборудования: DALI, управление устройствами по MQTT. *Трансляция собственного состояния в MQTT-топик (retained) допускается как опция.*
* НЕ обрабатывает микрологику датчиков: таймауты движения, подсветку соседних зон, диммирование по присутствию. Это `zone_manager` и его скрипты.
* **Периметр заканчивается на помещении.** Зоны внутри помещения (`light.<room>_<n>`) и отдельные светильники — зона ответственности системы датчиков.
* НЕ ведёт топологию здания и не создаёт групповые светильники.
* НЕ управляет ситуативными сценами помещений (актовый зал: театр, ивент, БЦТ).
* НЕ контролирует исполнение команд и здоровье устройств.
* Аварийного режима нет. Режимов управления ровно два: Авто и Ручной, задаются для здания и для каждого этажа; режим здания абсолютен.

**Сценарии пользователя (BDD, Given / When / Then):**

*Сценарий: Смена режима по расписанию без задержки*
* Дано: Режим управления «Авто», здание в режиме «Урок»; профиль режима «Перемена» одинаков для всех помещений второго этажа.
* Когда: Источник расписания активирует событие типа `break`.
* Тогда: Интеграция меняет состояние сущности режима на «Перемена» и отправляет **одну** команду на этажный групповой светильник, а не команды по каждому помещению; публикует событие с `area_id`, `floor_id`, `new_mode`, `previous_mode`, `source`.

*Сценарий: Переопределение ломает однородность этажа*
* Дано: Для одного помещения этажа профиль режима «Перемена» переопределён.
* Когда: Здание переходит в «Перемена».
* Тогда: Каскад не отправляет команду на этажную группу, а разворачивается до общих групп помещений; родительская и дочерняя группы не получают команд одновременно.

*Сценарий: Смена режима с системной задержкой*
* Дано: Здание в режиме «Перемена»; для «Урок» задана задержка 5 минут.
* Когда: Источник расписания активирует событие типа `lesson`.
* Тогда: Публикуется предупреждающее событие, выдерживается задержка без блокировки событийного цикла, затем выполняются действия и публикуется итоговое событие.

*Сценарий: Расписание сменилось во время задержки*
* Дано: Идёт отсчёт задержки перехода в «Урок», предупреждение опубликовано.
* Когда: Источник расписания переключается на `break` до истечения задержки.
* Тогда: Отложенный переход отменяется, публикуется событие отмены, запускается задержка режима «Перемена». Переход в «Урок» не выполняется.

*Сценарий: Режим запрещает работу датчиков*
* Дано: Здание переходит в режим «Перемена», профиль которого запрещает работу датчиков.
* Когда: Каскад применён.
* Тогда: Сущность «датчики разрешены» на каждом этаже переходит в `off`; автоматизации датчиков продолжают срабатывать по триггеру, но завершаются на условии, не вызывая `zone_manager.get_sensor_config` и не отправляя команд на шину DALI.

*Сценарий: Оркестратор недоступен*
* Дано: Автоматизации датчиков настроены с гейт-условием на сущность Оркестратора.
* Когда: Интеграция выгружена или её сущности стали `unavailable`.
* Тогда: Условие пропускает срабатывание (логика «не равно `off`»), освещение по датчикам продолжает работать. Здание не остаётся без света из-за сбоя интеграции.

*Сценарий: Ручной режим отдельного этажа*
* Дано: Здание в «Авто», третий этаж переведён в «Ручной».
* Когда: Расписание переходит в «Перемена».
* Тогда: Каскад применяется ко всем этажам, кроме третьего; на третьем действия не выполняются, датчики запрещены. Режим расписания продолжает вычисляться и отображаться.

*Сценарий: Возврат этажа в автоматический режим*
* Дано: Третий этаж в «Ручном»; здание за это время перешло в «Не рабочее время».
* Когда: Диспетчер возвращает этаж в значение «По зданию».
* Тогда: К этажу немедленно применяется профиль актуального режима, **без выдержки задержки**.

*Сценарий: Глушение здания перекрывает настройку этажа*
* Дано: Третий этаж в значении «По зданию».
* Когда: Здание переводится в «Ручной».
* Тогда: Автоматика молчит на всех этажах; изменить это настройкой этажа невозможно.

*Сценарий: Помещение исключено из управления расписанием*
* Дано: Помещение «Актовый зал» помечено меткой исключения.
* Когда: Здание переходит в «Перемена».
* Тогда: Действия к этому помещению не применяются, свет в нём не меняется; каскад по этажу разворачивается до уровня помещений; в мониторинге помещение отображается как пропущенное.

*Сценарий: Источник расписания недоступен*
* Дано: Здание в режиме «Урок».
* Когда: Сущности `event_schedule` становятся недоступны либо ни одно событие не активно.
* Тогда: Интеграция переходит в fallback-режим («Не рабочее время» по умолчанию), помечает состояние признаком недоступности источника и применяет профиль fallback-режима.

*Сценарий: Наложение событий расписания*
* Дано: Одновременно активны события типов `lesson` и `break`.
* Когда: Машина состояний вычисляет режим.
* Тогда: Выбирается «Перемена» согласно приоритету `break > window > lesson > off`, факт наложения записывается в лог как аномалия источника.

*Сценарий: Перезапуск Home Assistant с расхождением*
* Дано: Перед остановкой здание было в «Урок»; за время простоя расписание перешло в «Не рабочее время».
* Когда: Home Assistant запускается.
* Тогда: Интеграция вычисляет актуальный режим, обнаруживает расхождение и применяет профиль без задержки. Если расхождения нет — состояние восстанавливается без применения действий. Сущности «датчики разрешены» выставляются по режиму в обоих случаях.

*Сценарий: Нарушен инвариант Area*
* Дано: В Area помещения помимо общей группы оказалась вторая световая сущность — лампа или зонная группа.
* Когда: Здание переходит в новый режим.
* Тогда: Каскад по этому помещению **не выполняется**, Area помечается в мониторинге как ошибка конфигурации; остальные помещения обрабатываются штатно. Дублирующих команд на шину не отправляется.

*Сценарий: Настройка профиля инженером*
* Дано: Открыта Custom Panel, пользователь — администратор; помещения заведены в реестре HA, групповые светильники созданы и назначены в Areas генератором.
* Когда: Инженер задаёт для помещения профиль режима «Урок».
* Тогда: Панель отправляет точечную операцию через WebSocket, ядро валидирует её и сохраняет по ключу `area_id`; изменение применяется без перезагрузки HA. Параллельно открытая вторая вкладка не затирает чужие правки.

*Сценарий: Помещение переименовано или перемещено в реестре HA*
* Дано: Для помещения настроен профиль.
* Когда: Инженер переименовывает помещение либо переносит его на другой этаж.
* Тогда: Профиль сохраняется (ключ — `area_id`), при переносе наследование пересчитывается по новому этажу.

*Сценарий: Помещение удалено из реестра HA*
* Дано: Для помещения настроен профиль.
* Когда: Помещение удаляется в настройках Home Assistant.
* Тогда: Интеграция продолжает работать, профиль сохраняется и помечается как осиротевший, в мониторинге это видно.

*Сценарий: Неадминистратор пытается изменить профиль*
* Дано: Пользователь без прав администратора открыл панель.
* Когда: Он пытается выполнить операцию правки профиля.
* Тогда: Операция отклоняется ядром; переключение Авто/Ручной и просмотр мониторинга остаются доступны.

**Как будет проверяться результат (измеримые критерии):**
* Покрытие ветвей unit-тестами > 90% для модулей машины состояний (вычисление режима, приоритеты, fallback, отмена отложенных переходов, правило схлопывания).
* Логика тестируется **без `hass`** — пакет `homeassistant` в проекте не используется, тестов с ним нет. Это обязательное архитектурное требование: всё, что можно посчитать чистой функцией, считается чистой функцией. Сюда входят приоритет расписания, fallback, наследование профилей, правило схлопывания, проверка инварианта Area, решение об отмене отложенного перехода, **сериализация и миграция схемы хранилища**.
* 0 ошибок линтера (`ruff check`) и 0 ошибок строгой типизации (`mypy --strict`) — по нашему коду. ⚠ Без установленного пакета `homeassistant` типы HA недоступны, `import-not-found` подавлен, и корректность использования HA-API **не проверяется ни тестами, ни типами**. Обвязка держится только на ревью и полевом тесте.
* Функции сериализации и миграции схемы покрыты тестами как чистые преобразования данных; фактическая запись в `.storage` проверяется вручную на полевом тесте.
* Ручной чек-лист из `.ai/rules/tooling.md` §5 пройден и зафиксирован в протоколе: установка через UI, отсутствие дублей обработчиков после перезагрузок, сохранность конфигурации при рестарте, миграция на реальном файле, чистый лог без блокирующих вызовов и deprecated-предупреждений, работа панели и отказ неадмину.
* В реестре сущностей и логах отсутствуют динамически создаваемые `script.*` / `automation.*`; вызовов `automation.turn_on/off` в коде нет.
* В логах Home Assistant отсутствуют предупреждения `Detected blocking call inside the event loop`.
* Каскад никогда не отправляет команду родительской и дочерней группе одновременно — проверяется тестом на правиле схлопывания.
* Инвариант «одна световая сущность в Area» проверяется до применения каскада; при нарушении команда не отправляется, а Area помечается ошибкой — покрыто тестом.
* Агрегатная Area этажа опознаётся по метке, а не по имени — тест подтверждает, что переименование Area не ломает различение.
* Событие смены режима содержит `area_id` и `floor_id`.
* Профили переживают переименование и перенос помещения; удаление помещения не приводит к падению.
* После многократной перезагрузки config entry число обработчиков событий не растёт.

**Контекст проекта:** Проект замещает фрагментированную архитектуру (колледж Химки), где логика была размазана по десяткам YAML-файлов. Масштаб — 5 этажей, порядка 20–50 помещений.

*Доменные термины:*
* **Оркестратор** — эта интеграция.
* **Объект / Этаж / Помещение / Зона / Светильник** — пять уровней. Периметр Оркестратора — от объекта до помещения включительно; зоны и светильники ведёт система датчиков.
* **Этаж** — Floor в реестре HA, групповой светильник `light.ves_<N>_i_etazh`.
* **Помещение** — Area в реестре HA, групповой светильник `light.<room>_obshchii`.
* **Зона** — `light.<room>_<n>`, единица работы датчика движения. **Вне периметра.**
* **Профиль режима** — набор действий (задержка + сервисные вызовы), применяемый при наступлении режима.
* **Режим управления** — Авто или Ручной; для здания и для этажа.
* **Режим расписания** — Урок / Перемена / Не рабочее время / Окошко.
* **Гейт** — сущность «датчики разрешены», которую проверяет условие в blueprint автоматизаций датчиков.
* **Схлопывание** — выбор самого высокого уровня групп, на котором результат каскада однороден.

## Что изменилось в редакции 5

* **Принята политика «в Area — одна световая сущность»**: только групповой светильник уровня, лампы и зонные группы туда не попадают. Делает целеуказание по Area корректным для всех потребителей, включая дашборд и голосовые команды.
* **Целеуказание вернулось к `area_id`** и оказалось надёжнее хранения `entity_id` — не страдает от ловушки `unique_id` ≠ `entity_id`. Идея экспорта карты топологии из генератора отпала.
* **Добавлена рантайм-проверка инварианта**; при нарушении каскад по Area не выполняется.
* **Агрегатная Area этажа различается по метке**, а не по имени.
