# PLAN — интеграция «Building Automation» (Оркестратор здания)

План разработки. Версия 1.7, 2026-08-11. Основан на [`SPEC.md`](SPEC.md) v1.5.

## Как это работает (логика перед планированием)

Прежде чем резать на этапы — сквозной поток в рантайме. Он же объясняет порядок
этапов: сначала тонкая нить через все слои, потом наращивание.

**Один цикл обработки события:**

```
1. Событие  → coordinator (оболочка)
   ScheduleChanged | ControlModeChanged | TimerFired | Started
   (изменение реестра и reapply — НЕ входы ядра: оболочка пересобирает
    снимок топологии и вызывает decide с обычным входом, SPEC §2.2.5)

2. coordinator собирает СНИМКИ через адаптеры:
   registry.py → TopologySnapshot   (этажи, помещения, метки, статус Area)
   schedule.py → ScheduleEvent[]     (сущности event_schedule)
   + текущее OrchestratorState из памяти

3. ЯДРО (чистая функция, без hass):
   decide(state, input, now) → Decision
     внутри: resolve_schedule_mode → resolve_actions → plan_cascade
   Decision = новое состояние
            + CascadePlan (команды по area_id, или пусто)
            + TimerOp (SetTimer | CancelTimer | NoTimerOp)
            + доменные события
            + значения гейтов по этажам

4. coordinator ИСПОЛНЯЕТ Decision через адаптеры:
   executor.py  → сервисные вызовы light/switch по area_id (изоляция сбоев)
   timers.py    → async_call_later / отмена
   publisher.py → события на шину + состояния в сущности
   entities     → select/switch/sensor/binary_sensor обновляются

5. Задержка: если Decision содержит SetTimer, каскад отложен.
   По истечении приходит TimerFired → снова decide → каскад применяется.
```

**Инварианты, которые держит эта конструкция** (из SPEC):

- `decide` детерминирована: время приходит параметром `now`, тех же входах — тот
  же выход. Это условие воспроизводимости тестов.
- Ровно **один** отложенный переход в любой момент (одна задержка на здание,
  SPEC §7.4): отмена — присваивание поля, не обход коллекции.
- **Инвариант Area** проверяется до каскада: в целевой Area ровно одна световая
  сущность, иначе каскад по ней не идёт (SPEC §3.2 ТЗ).
- **Схлопывание** до однородного уровня: команда родителю и потомку в одном
  плане не встречается (SPEC §5.3 ТЗ).
- **Гейт fail-open**: Оркестратор публикует `binary_sensor` на этаж; blueprint
  читает его шаблоном `{{ states(gate) != 'off' }}` — отсутствие гейта разрешает
  работу датчиков (SPEC §7.3).

**Почему такой порядок этапов.** Ядро тестируемо (чистые функции), обвязка HA —
нет (пакет `homeassistant` не ставится, SPEC §2.1). Отсюда конфликт: TDD тянет
начать с ядра (безопасно), а минимизация риска — рано потрогать обвязку
(непокрыта, опасна, проверяется только на объекте). Разрешается **tracer
bullet**: этап 1 проводит одну тонкую нить (режим расписания) через все слои и
уже разворачивается на объекте — ранняя проверка setup/entity/coordinator. Затем
этапы 2–6 наращивают ядро под полным TDD, этап 7 достраивает исполняющую обвязку,
8–9 — API и панель, 10 — сборка и полевой тест.

## Дисциплина TDD (из skill `tdd`)

Внутри каждого доменного этапа — **вертикальные срезы**, а не «все тесты, потом
весь код»:

```
RED→GREEN: тест 1 → реализация 1
RED→GREEN: тест 2 → реализация 2
...
REFACTOR (только на зелёном)
```

Один тест за раз, минимум кода под текущий тест, тест проверяет **поведение через
публичный интерфейс**, не детали реализации. Интерфейсы уже зафиксированы в
SPEC §2.2 и прошли ревью — на этом шаге они не пересогласовываются.

**Оболочка (адаптеры, сущности, coordinator, config_flow, WS, панель) не имеет
юнит-тестов** — пакета `homeassistant` нет. Её этапы закрываются `mypy`,
`eslint`/`tsc` и **ручным чек-листом** из `.ai/rules/tooling.md` §5. Это отражено
в критериях завершения таких этапов явно.

## Этап 1 — Tracer bullet: режим расписания

**Цель.** Тонкая нить через все слои: интеграция ставится, читает

- Цикл: одно активное событие → приоритет при наложении → полный порядок

  тип. Один тест → одна реализация, по одному сценарию §5.1 за раз.

Под-этап **1a — ядро** (выше). Под-этап **1b — обвязка среза** (ниже): их можно
вести отдельными заходами, 1a самодостаточен и тестируем без 1b.

**Оболочка 1b (без юнит-тестов):**
- `adapters/schedule.py`: сущности `event_schedule` → `ScheduleEvent[]`.

## Этап 6 — Машина состояний

**Цель.** `decide` — единственная точка политики «что делать сейчас». Связывает
schedule + profiles + cascade и решает про задержки, старт, ручные режимы, гейты.

**Ядро (TDD, сценарии SPEC §5.5):**
- `domain/machine.py`: `decide(state, input, now) → Decision`.
- `Input` и `Decision` по SPEC §2.2.5; время — параметр `now`.
- Цикл: смена без задержки → немедленно → смена с задержкой → SetTimer +
  предупреждение, без плана → таймер применяет → новая смена в задержке отменяет
  прежний (CancelTimer + событие отмены + новый SetTimer) → старт при совпадении
  (без действий, но гейты выставлены) → старт при расхождении (план без задержки)
  → незавершённая задержка не восстанавливается → ручное здание глушит и
  закрывает гейты → ручной этаж не влияет на другие → возврат этажа применяет без
  задержки → гейт этажа берёт переопределение режима → режим расписания
  вычисляется и в Ручном → повторный `decide` детерминирован.

**Критерий завершения:**
- Ядро §5.5: покрытие ветвей `domain/machine.py` ≥ 95 %.
- Mutation score `machine.py` ≥ 70 %.
- `mypy --strict`, `ruff` — 0.
- Закрывает: SPEC §5.5. После этого этапа **всё ядро закрыто** — общий порог
  покрытия `domain/` ≥ 95 % и mutation ≥ 70 % на четырёх модулях логики (§6).

**Оценка: L.** При переполнении — под-этапы: 6a смена/задержка/отмена, 6b
старт/жизненный цикл, 6c ручные режимы и гейты.

## Этап 12 — целеуказание по метке `ba_area_light` (реализовано)

> ✅ **Выполнено 2026-08-07** (12a–12f). Итог — в «Changelog выполненных этапов».
> Ниже — исходный план работ.

**Цель.** Оркестратор целит помеченную (`ba_area_light`) световую сущность
вместо `area_id`. Снимает инвариант «ровно одна `light` в Area» и позволяет
держать в Area любой свет (лампы, зонные группы) для других интеграций и
удобства. Зависит от **Правки 6** генератора (метка) —
[`docs/contracts/contract-ha-lighting-compilers.md`](docs/contracts/contract-ha-lighting-compilers.md) §8.

**Что меняется (дизайн).**

- **Топология** (`domain/types.py` + `adapters/registry.py`): `Room` и `Floor`
  получают `light_entity_id: str | None` — помеченный `ba_area_light` светильник
  помещения / агрегата этажа. Адаптер отбирает light-сущности Area, оставляет
  помеченные: ровно одна → `OK` + сохраняем `entity_id`, 0 → `NO_LIGHT`, ≥2 →
  `MULTIPLE_LIGHTS`. `evaluate_area` остаётся чистой (считает переданный список),
  но список теперь — только помеченные.
- **Каскад** (`domain/cascade.py`, `Command`): цель светового потока — не
  `area_id`, а **световая сущность** (`Room.light_entity_id`; при схлопывании —
  `Floor.light_entity_id`). Room-pinned поток (автояркость) **остаётся по
  `area_id`** (сервис сам отбирает датчики). `Command` несёт цель одного из двух
  видов — вводим дискриминатор (свет-сущность / Area).
- **Исполнитель** (`adapters/executor.py`): свет → `{**data, "entity_id": …}`;
  автояркость → `{**data, "area_id": …}` (как сейчас).
- **`get_state`/панель:** в `last_plan.commands` цель света станет `entity_id`;
  `level` (этаж/помещение) — по совпадению с `Floor.light_entity_id`. Колонка
  «Инвариант» без изменений (статусы те же, но по помеченным).
- **Без миграции хранилища:** `Config` не меняется; топология пересобирается из
  реестра.

**Порядок (TDD, ядро вперёд):**

2. **12b — каскад:** цель светового потока = `light_entity_id`; дискриминатор

3. **12c — исполнитель** (адаптер, без юнит-тестов): диспетч entity_id/area_id.
